# Delivery workflow (illustrative)

Every work item should explain the user outcome, list observable acceptance criteria, name dependencies and link evidence of verification.

## Issue hierarchy

The delivery overview is the parent issue. Milestone workstreams are its real GitHub sub-issues. Smaller reviewable tasks may be nested beneath a workstream. A milestone groups work by review outcome, while the hierarchy explains how the work fits together.

## Updates and decisions

The developer posts short updates covering what changed, what was checked, what remains open and whether stakeholder input is needed. Actual stakeholder decisions must come from the stakeholder or be explicitly attributed to a confirmed conversation. This repository contains no simulated client approvals.

## Branches and pull requests

A focused branch contains a reviewable change. The pull request links the issue, describes the outcome and records verification. Only close an issue once its stated deliverable is complete. For the demonstration, the developer merges a documentation-only pull request without presenting that as an independent review.

## MVP boundaries to confirm

- Student profile creation and controlled updates before relevant fairs.
- University/programme data, profile management and matching presentation.
- Matching baseline using structured filters and keyword/semantic signals.
- Cost limits, measurable quality criteria and privacy requirements before launch.

This is a proposed working method, not an agreed product specification.
